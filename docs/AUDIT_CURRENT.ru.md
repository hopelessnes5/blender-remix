После аудита по баг-репорту закрыт дефект загрузки существующего мода в сцену (`Apply Mod File Changes`): `_get_changed_prims` добавляла в обработку все определённые прими стейджа, включая capture-слои и asset-файлы, приходящие по ссылкам, поэтому в сцену заново падала вся capture, а добавления спавнились рядом с существующими объектами. Второй раунд выстроил Apply по модели официального Toolkit-мода (референс `gameReadyAssets` Cod2 Carentan): плейсменты держит capture (`inst_<HASH>_<N>`), мод несёт только прототипы — `over/def mesh_<HASH>` со сбросом `references = None` и `ref_*`-детьми со ссылками на asset-файлы, света под путями мешей, перезаписи `over Looks`. Применяются не «все дефы», а только prims, чьи пути несут 16-символьный capture-хэш (`mesh_`/`inst_`/`light_`), встречающийся в тегах объектов сцены (`usd_instance_path`/`usd_prim_path`/`usd_prototype_path`/`usd_light_path`/`remix_mesh_hash`) или в путях, определённых capture-слоями; библиотеки чужих локаций в набор изменений не попадают. Для хэша, объекты которого уже есть в сцене, замена маршрутизируется на место: контент прототипа собирается в один mesh-datablock (трансформы частей запекаются в пространстве контейнера, как хранит capture-импорт), объекты переключаются через `obj.data` — матрицы, видимость и теги остаются от сцены; пустой сброс (`references = None`) вместо замены скрывает эти объекты. Новые размещения (`inst_<HASH>_<N>`), типированные света (один объект на свет, даже если он вложен под прототип) и прямые Mesh-дефы создаются в отдельной коллекции `mod <имя мода>` (из `lightspeed_mod_name`, fallback — stem файла / `mod`) как ребёнок коллекции сцены; повторная обработка одного прототипа/контейнера за прогон дедуплицируется. Текстуры прогреваются только для материалов, реально совпавших с объектами сцены. Границы: поворот Y-up применяется матрицей целиком (legacy-поведение), материалы Toolkit-неймспейса `mat_<32hex>` матчятся по именам объектов, а не по 16-символьному хэшу, инстанс-матрицы объектов сцены не перезаписываются, поведение в игре не проверялось. Тест: `tests/blender/test_mod_apply_changed_prims.py`.

Третий раунд (реальный прогон nfsc_remix): замена текстур не происходила, а объекты появлялись в (0,0,0). Исправления: записи `over "Looks"/*` с шейдерами отсекались хэш-гейтом (путь не несёт mesh-хэш) — теперь они минуют его, привязка материалов к сцене идёт через существующие сканы привязок (binding-скан, матчинг по именам материалов, scoped к хэшам мода); over-записи на `over mesh_<HASH>` (флаги категорий, перебиндинги внутри прототипа) не подменяют геометрию — их `material:binding` применяется к объектам того же хэша (`_apply_material_to_hash_objects`) без трансформов; главный источник нулей найден на реальном моде: binding-скан добавлял bound-примы в change set как «обычные» изменения, и композированная матрица (identity, когда мод не пишет трансформов) перезаписывала размещение сцены — такие пути теперь обрабатываются только материалами (`_material_scan_prim_paths`); создание света с цветовой температурой падало на не существующих в API именах `use_custom_color_temp`/`color_temperature` (AttributeError) — температура Toolkit уходит в нативную температуру света Blender (`use_temperature`/`temperature`), цвет `light.color` остаётся тинтом без температуры, нативное чёрное тело даёт итоговый цвет; базовый цвет и Кельвины запоминаются как свойства, чтобы повторные прогоны не накапливали тинт (то же в `_apply_light_properties` для существующего света и в `sync_ops.py`). Проба повторена после перевода на нативную температуру. Контрольная проба на полной копии nfsc_remix: 7 сентинелов на (10, 20, 30) не сдвинулись, 4 света созданы на координатах мода (включая DistantLight 15000 K), 523 изменённых материала найдено через шейдерные over-записи, 0 предупреждений. Тесты: фикстура двух тегов и over-флагов, материальный rescope на объекты своего хэша, тёплый свет с температурой; расширенный набор 332 теста зелёный в Blender 4.5.5 LTS и 5.1.2.

При исследовании A05 сохранение целевого USD через временный файл осталось экспериментом и не включено в аддон. На временных NTFS-файлах Windows `os.replace` удалил альтернативный поток данных; `ReplaceFileW` сохранил поток в проверенном случае, но изменил флаги наследования DACL. SACL не удалось прочитать в текущем контексте из-за отсутствия `SeSecurityPrivilege`; привилегии и ACL не изменялись. Перед внедрением замены файла нужно решить сохранение метаданных и восстановление после ошибок; проверка только содержимого USD недостаточна.
